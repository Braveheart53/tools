Matching the GPU stack to the card, and the settings that decide placement

A model runs at GPU speed only when four things agree: the card's architecture, the driver, the toolkit the runtime was built with, and the runtime settings that decide how much of the model and its cache stay in video memory. This page sets out each of the four for NVIDIA, AMD, Intel and Apple hardware, for both runtimes in the set.

Everything here was read from the runtimes' own sources on 2026-11-15[40][41][42][43]. Two things changed recently enough to break older guides, including some pages in this set: CUDA 13 can no longer build for GTX 10-series cards[45][44], and llama.cpp now fits a model to memory on its own unless you tell it not to[43].

1. Start from the card

For NVIDIA cards the number that decides everything downstream is the compute capability: a version number for the GPU architecture. It decides which driver Ollama will accept, which CUDA toolkit can compile for the card, and which value goes into CMAKE_CUDA_ARCHITECTURES when llama.cpp is built for it. Look the card up in NVIDIA's list[49] or in Ollama's table[40] before downloading anything.

If your card is Pascal, Maxwell or Volta, CUDA 13 is the wrong toolkit for building. NVIDIA's release notes record the removal of Maxwell, Pascal and Volta support[45], and llama.cpp only adds its 50-virtual 61-virtual 70-virtual targets when the toolkit is older than 13[44]. The build notes in the deployment folder target CMAKE_CUDA_ARCHITECTURES=61, which is Pascal, so those machines stay on CUDA 12.x. Running Ollama is unaffected: it ships its own runtime and only needs a driver of version 570 or newer for these cards[40].

AMD, Intel and Apple hardware do not use compute capability. For AMD, what matters is whether the card is on ROCm's support list (section 3); everything else runs through Vulkan (section 5).

2.2 Building llama.cpp with CUDA

The documented build is two commands[42]. With GGML_NATIVE on (the default) and a recent CMake, llama.cpp builds for the GPU in the build machine and nothing else[44]; set the architecture explicitly only when building for a different machine:

# In a "Developer PowerShell for VS 2022" (Pascal, CUDA 12.x) or VS 2026 (CUDA 13.5)
cmake -B build -DGGML_CUDA=ON
cmake --build build --config Release -j

# Building for another machine's card: name its compute capability without the dot.
# 61 = Pascal (GTX 10-series), 86 = RTX 30-series, 89 = RTX 40-series.
cmake -B build -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES="61"

The explicit-architecture form follows the documented example -DCMAKE_CUDA_ARCHITECTURES="86;89"[42]. The scripts/build_cpp.ps1 wrapper on the build-and-test page sets up the Visual Studio environment for you.

3. AMD: ROCm, HIP, WSL and Vulkan

AMD cards reach the runtimes by two routes. ROCm (and its HIP compiler) is AMD's compute stack and the faster route, but it supports a specific list of cards, and the list differs between Linux, Windows and WSL. Every other recent Radeon runs through Vulkan, which needs nothing beyond the normal driver on Windows[40].

Which AMD cards Ollama runs through ROCm, by platform[40], and which AMD supports for ROCm inside WSL[52]. Cards outside a row's list fall back to Vulkan.

3.1 Cards just outside the Linux list

On Linux, Ollama can be told to treat an unsupported card as a close supported target with HSA_OVERRIDE_GFX_VERSION. Its own example maps an RX 5400 (gfx1034) onto gfx1030 with HSA_OVERRIDE_GFX_VERSION="10.3.0", and per-device forms (HSA_OVERRIDE_GFX_VERSION_0, _1) exist for mixed cards[40]. This is a Linux mechanism; the older Jupyter pages in this set that compute it inside WSL are not following a documented procedure.

3.2 ROCm inside WSL, and what it cannot do

AMD's current WSL procedure is: install the Adrenalin driver version listed for your ROCm release, install WSL with Ubuntu 22.04 or 24.04, then install the ROCDXG user-mode library[87]. It does not install Linux kernel modules: WSL runs Microsoft's kernel. The ROCDXG repository is itself marked deprecated, its source having moved into AMD's rocm-systems tree[88], so follow AMD's how-to page[87] for the commands rather than any copy of them, this page included.

amd-smi does not work under WSL. AMD's limitations page states that "due to WSL architectural limitations for native Linux User Kernel Interface (UKI), amd-smi is not supported"[53]. Anything that reads AMD GPU metrics through amd-smi inside WSL, including amd_smi_exporter, cannot report the GPU there. Section 13 gives the route that works on Windows.

3.3 Building llama.cpp with HIP

The documented Linux build[42]; GPU_TARGETS "is optional, omitting it will build the code for all GPUs in the current system":

HIPCXX="$(hipconfig -l)/clang" HIP_PATH="$(hipconfig -R)" \
    cmake -S . -B build -DGGML_HIP=ON -DGPU_TARGETS=gfx1030 -DCMAKE_BUILD_TYPE=Release \
    && cmake --build build --config Release -- -j 16

Building natively on Windows needs AMD's HIP SDK[54]. Neither is needed to run Ollama or a prebuilt llama.cpp HIP release.

5. Vulkan, the cross-vendor path

Vulkan is the route for any card that ROCm or CUDA does not cover, and the one the multi-node guide in this set builds on. In Ollama it "is enabled by default when the backend is installed", and on Windows "most GPU vendors drivers come bundled with Vulkan support and require no additional setup steps"[40]. Linux needs the vendor's or Mesa's Vulkan driver, and on Linux Ollama needs cap_perfmon or root to read free VRAM through Vulkan; without it, it schedules from approximate model sizes[40].

Building llama.cpp's Vulkan backend (-DGGML_VULKAN=ON) needs the Vulkan SDK on the build machine[42]; running it needs only the driver. The SDK in the deployment folder is 1.4.350.0 and the current one is 1.4.363.1[63]. Per-node device selection for AMD cards over Vulkan is covered in the multi-node guide.

7. How Ollama places a model

Ollama decides placement itself from the VRAM each GPU library reports. The settings below change its inputs. Names and descriptions are from the server's own configuration source[41] and its FAQ[9]; set them on the server process, which on Windows means the user or system environment, then restart Ollama.

To see where a loaded model ended up, run ollama ps: the PROCESSOR column reads 100% GPU when the whole model is in video memory, and shows a CPU/GPU split when part of it is not[9]. A split is the single most common reason a model is slower than the model page predicts.

When OLLAMA_CONTEXT_LENGTH is unset, Ollama picks the default context from total VRAM; the thresholds in the code are 23 and 47 GiB rather than the 24 and 48 the prose states. The build-and-test page has the table[35][38].

8. How llama.cpp places a model

Current llama.cpp builds fit a model to memory automatically. With --fit on, the default, the server adjusts every argument you did not set, layer count and context included, until each device keeps a free margin[43]. Options and defaults below are from common/arg.cpp and common/common.h[43].

What --fit guarantees on each device

Derived here
\[ V_{\text{tot},d} - \bigl(S_{w,d} + S_{kv,d} + V_{\text{rt},d}\bigr) \;\ge\; m_{\text{fit},d} \quad \text{for every device } d, \qquad n_{\text{ctx}} \;\ge\; n_{\text{ctx,min}} \]

llama.cpp's option text says --fit decides "whether to adjust unset arguments to fit in device memory", with --fit-target giving a "target margin per device" and --fit-ctx the "minimum ctx size that can be set by --fit"[43]. Written as an inequality, that is the condition above. The order in which it gives up layers versus context is not stated in the option text; --fit-print on prints the estimate it used.

  1. Quoted defaults from common/common.h[43]: fit_params is on, fit_params_target is \( 1024 \times 1024 \times 1024 \) bytes per device (the 1024 MiB the option text reports), and fit_params_min_ctx is 4096.
  2. Device \( d \) holds its share of the weights \( S_{w,d} \), its share of the key/value cache \( S_{kv,d} \) (the cache is split with the layers in the default layer split mode), and the runtime reservation \( V_{\text{rt},d} \).
  3. Reading "margin" as the memory left free once those are allocated gives \( V_{\text{tot},d} - (S_{w,d} + S_{kv,d} + V_{\text{rt},d}) \ge m_{\text{fit},d} \). This reading is ours; the option text does not define the term further.
  4. The context may be reduced to meet the margin, but not below \( n_{\text{ctx,min}} \).
  5. Only unset arguments are adjusted. An explicit -ngl or -c is held fixed, so a hand-tuned service definition opts out of the mechanism for that argument.

SymbolMeaningUnit

\(S_{kv,d}\)Key/value cache bytes placed on device \(d\)B

The service definitions in this set pass -ngl explicitly. An explicit value is held fixed, so those services do not benefit from --fit for the layer count. On a single machine, removing -ngl lets the server choose; keep an explicit value where you need placement to stay identical across restarts. Whether --fit accounts for RPC workers was not established from the option text, so keep explicit values on RPC clusters.

When you do set the layer count yourself, start from this:

Layer count to pass to --n-gpu-layers

Derived here
\[ n_{\text{gpu}} \;=\; \left\lfloor \frac{\bigl(V_{\text{tot}} - V_{\text{rt}} - S_{kv}\bigr)\,n_{\ell}}{S_{w}} \right\rfloor, \qquad 0 \le n_{\text{gpu}} \le n_{\ell} \]

Current llama.cpp builds default to -ngl auto with --fit on, which adjusts every argument you did not set until the model fits (next relation)[43]. This relation is for when you set -ngl yourself, as the service definitions in this set do: an explicit value is not adjusted, so the failure mode of overshooting is an out-of-memory abort part-way through loading rather than a graceful fallback.

  1. llama.cpp offloads whole transformer blocks, so the granularity is one layer. Averaged over the stack, one layer is \( S_{w}/n_{\ell} \) bytes.
  2. The device must also hold the runtime reservation \( V_{\text{rt}} \) and the whole key/value cache \( S_{kv} \), both of which are allocated regardless of how many layers are resident.
  3. The bytes left for weights are therefore \( V_{\text{tot}} - V_{\text{rt}} - S_{kv} \).
  4. Divide by the per-layer size and take the floor: \( n_{\text{gpu}} = \lfloor (V_{\text{tot}} - V_{\text{rt}} - S_{kv})\,n_{\ell}/S_{w} \rfloor \).
  5. Clamp into \( [0,\,n_{\ell}] \), then subtract one or two before the first run. Layers are not uniform in size, the output projection is usually the largest single tensor, and allocator fragmentation costs real megabytes.
  6. If the result equals \( n_{\ell} \), pass -ngl all (accepted by current builds[43]; older builds need -ngl 999) rather than the exact count, so the setting survives a change of model.

9. Mixture-of-experts models on a small card

Most of the strongest open models in the shortlist are routed mixtures of experts: they occupy memory like their total size and stream like their active subset (model page, section 3.3). That asymmetry is what makes the options below worthwhile. Moving the expert weights to system memory frees the most VRAM for the least speed, because each token reads only the few experts it is routed to.

llama.cpp mixture-of-experts placement options[43].
OptionEnvironmentMeaning

-ncmoe, --n-cpu-moe NLLAMA_ARG_N_CPU_MOEKeep the MoE weights of the first N layers in the CPU
--moe-cache-mib N—GPU cache for the experts kept in the CPU; default 0 (disabled)
-ot, --override-tensorLLAMA_ARG_OVERRIDE_TENSOROverride the buffer type of tensors matching a name pattern; the general form of the options above

Keeping mixture-of-experts weights in system memory

Derived here
\[ S_{\text{gpu}} \;\approx\; S_{w} - N_{\text{cpu}}\,\frac{S_{\text{exp}}}{n_{\text{moe}}}, \qquad t_{\text{tok}} \;\approx\; \frac{S_{\text{act}} - N_{\text{cpu}}\,a}{B_{\text{gpu}}} + \frac{N_{\text{cpu}}\,a}{B_{\text{cpu}}}, \qquad a \;=\; \frac{k}{E}\,\frac{S_{\text{exp}}}{n_{\text{moe}}} \]

--n-cpu-moe N "keep[s] the Mixture of Experts (MoE) weights of the first N layers in the CPU"[43]. The relation shows why that costs so much less speed than lowering -ngl by the same memory: a token reads only the \( k \) routed experts of each layer, so the CPU streams a fraction \( k/E \) of those layers' expert bytes, not all of them.

  1. Split the weights into expert tensors \( S_{\text{exp}} \), spread over \( n_{\text{moe}} \) MoE layers, and everything else (attention, shared experts, embeddings). Assume the expert bytes are equal across MoE layers.
  2. Moving the experts of \( N_{\text{cpu}} \) layers to system memory removes \( N_{\text{cpu}}\,S_{\text{exp}}/n_{\text{moe}} \) from the card, which gives \( S_{\text{gpu}} \).
  3. Each layer has \( E \) experts and routes each token to \( k \) of them, so a token reads \( a = (k/E)\,S_{\text{exp}}/n_{\text{moe}} \) expert bytes per MoE layer. This is the per-layer form of the active-parameter relation on the model page.
  4. By the bandwidth-ceiling argument, the GPU part of a token costs its bytes over \( B_{\text{gpu}} \) and the CPU part its bytes over \( B_{\text{cpu}} \). The two run in sequence for one token, so they add, giving \( t_{\text{tok}} \).
  5. Neglected: moving activations across PCIe (small per token), CPU compute speed (the CPU side can be compute-bound rather than bandwidth-bound), and the optional --moe-cache-mib GPU cache for offloaded experts[43]. Treat \( t_{\text{tok}} \) as a lower bound and measure.

The practical method: let --fit place everything, and if the context it chooses is too short, raise --n-cpu-moe until the context you need fits, measuring token rate at each step with the probe script on the model page. Ollama does not expose these options.

10. Cache type and attention kernel

After the weights, the key/value cache is the largest allocation, and it grows linearly with context and with parallel slots:

Key/value cache footprint

Derived here
\[ S_{kv} \;=\; 2\,n_{\ell}\,n_{kv}\,d_{h}\,L_{\text{ctx}}\,n_{\text{seq}}\,b_{kv} \]

The cache is the term people forget. It is linear in context length and linear in the number of concurrent sequences, so raising --ctx-size from 8192 to 32768 while also raising --parallel from 1 to 4 multiplies this term by sixteen.

  1. Autoregressive attention caches one key vector and one value vector for every token already generated, for every attention layer. That is the leading factor of 2.
  2. Grouped-query attention shares each key/value pair across several query heads, so the count that matters is \( n_{kv} \), the number of key/value heads, not the number of query heads.
  3. Each cached vector has \( d_{h} \) components, so one token costs \( 2\,n_{\ell}\,n_{kv}\,d_{h} \) elements.
  4. Multiply by the context length \( L_{\text{ctx}} \) that the cache is sized for, and by the number of concurrent sequences \( n_{\text{seq}} \) (--parallel in llama-server), each of which keeps its own cache.
  5. Multiply by the bytes per cached element \( b_{kv} \). Ollama exposes this as OLLAMA_KV_CACHE_TYPE, documented with a default of f16 and options q8_0 and q4_0[9], giving \( b_{kv} = 2,\ 1,\ 0.5\ \mathrm{B} \) respectively. Reducing \( b_{kv} \) below 2 is conditional: the cache can be quantised only “when Flash Attention is enabled”[9], so on a backend or device without it the setting does not buy the memory this step assumes.

Share of the model each GPU receives under --tensor-split

Derived here
\[ f_{i} \;=\; \frac{t_{i}}{\sum_{j=1}^{G} t_{j}}, \qquad S_{w,i} \;\approx\; f_{i}\,S_{w}, \qquad t_{i} \;\propto\; V_{\text{tot},i} - V_{\text{rt},i} \;\;\text{to balance free memory} \]

The option takes "a comma-separated list of proportions, e.g. 3,1" giving the "fraction of the model to offload to each GPU"[43]. Proportions are normalised, so 3,1 and 75,25 mean the same split.

  1. A list of proportions describes a split only once normalised, which gives \( f_{i} = t_{i}/\sum_j t_{j} \) with \( \sum_i f_{i} = 1 \).
  2. In the default layer mode whole layers are assigned, so \( S_{w,i} \approx f_{i}\,S_{w} \) holds to within one layer's size.
  3. For two unequal cards, setting \( t_{i} \) to each card's memory after its runtime reservation gives both the same fraction of free memory. Because the cache is split with the layers, the cache then divides in the same proportion.

Ollama exposes none of these; it decides placement itself, and OLLAMA_SCHED_SPREAD forces it to spread a model over every GPU rather than keep it on one[41]. Across machines the split is llama.cpp's RPC backend, covered on the multi-node guide and costed on the model page.

13.1 The Windows GPU collector

The gpu collector is off by default[55]. Add it to the default set with the documented [defaults] placeholder[86]:

# Command line (also the form for an NSSM or sc.exe service definition)
.\windows_exporter.exe --collectors.enabled "[defaults],gpu"

# MSI install: the same list through the installer property
msiexec /i windows_exporter-0.32.1-amd64.msi --% ENABLED_COLLECTORS="[defaults],gpu"

The MSI form passes the [defaults],gpu list through ENABLED_COLLECTORS, which the README describes as taking the same list as the flag[86]. Derived here: the README's own MSI examples list collectors explicitly.

Utilisation comes from a busy-time counter, so it needs rate(). The documented query[55]:

sum by (phys) (
  rate(windows_gpu_engine_time_seconds_total{phys="0", engtype="3D"}[1m])
) * 100

The metric was renamed between versions. It is windows_gpu_engine_time_seconds in 0.31.7, the version in the deployment folder, and windows_gpu_engine_time_seconds_total in 0.32.x[55]. A panel written for one shows nothing on the other. Compute work may run on an engine other than 3D; list the engine types your driver reports with count by (engtype) (windows_gpu_engine_time_seconds_total) before choosing one.

Utilisation from a cumulative busy-time counter

Derived here
\[ U(w) \;=\; \frac{c(t) - c(t-w)}{w} \;=\; \mathrm{rate}\bigl(c[w]\bigr), \qquad 0 \le U \le n_{\text{dev}} \]

Worth stating explicitly because the GPU exporters publish both kinds of metric and they are not interchangeable: a cumulative busy-seconds counter must be differenced, while an instantaneous percentage gauge must not be. Applying rate() to a gauge, or omitting it on a counter, are the two failure modes that produce plausible-looking but wrong dashboards.

  1. A busy-time counter \( c(t) \) accumulates seconds during which the device was executing work, and only ever increases.
  2. Over a window \( w \) the device was busy for \( c(t) - c(t-w) \) seconds out of \( w \) seconds elapsed.
  3. The ratio of those two is the fraction of wall-clock time the device was busy, which is the definition of utilisation.
  4. That ratio is precisely what PromQL rate() computes over a counter. The function reference states that breaks in monotonicity, such as a counter reset when the exporter or driver restarts, are adjusted for automatically[19], which is why the raw difference must not be taken by hand.
  5. When the counter aggregates \( n_{\text{dev}} \) devices the result saturates at \( n_{\text{dev}} \) rather than 1, so divide by the device count before plotting a percentage.
  6. \( w \) must satisfy the window condition derived above, otherwise the panel empties whenever a scrape is missed.

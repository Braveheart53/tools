AI_Local · v0.0.6 · Start here

Running AI on your own hardware, end to end

A working set for deploying language models across a home or lab network: choosing the hardware path, serving models on one machine or several, letting a model write, build and test code on machines you own, and monitoring what the hardware is doing. Follow the ten numbered steps below in order; each one ends with a check that tells you it worked.

Scientific and code-building work is the focus. Every page cites its sources to a numbered row in one reference table, every equation carries a variable table with units, and every figure that is an estimate rather than a citation says so.

Your setup

Pick the closest shape. Steps that do not apply are dimmed rather than hidden, so you can see what you are skipping.

On one machine, monitoring (steps 7–10) is optional: ollama ps answers the question a dashboard would. Steps 1–5 are the whole job.

With two machines, the monitoring steps earn their place: they are how you see that the second machine is actually being used.

With RPC workers, build llama.cpp on every node for its own card (step 2 explains why mixed generations need different CUDA versions), and do every monitoring step.

No setup chosen: every step is shown.

GPU vendor shortcuts: NVIDIA · AMD · Intel and Apple · any vendor through Vulkan

3. Which model, and will it fit?

Stage 1 turns on two questions that have to be answered together: which model to run, and whether your card can actually hold it. Reading someone else’s worked example is a poor substitute for either, so both are evaluated here against your own hardware. The arithmetic is the same as the model selection page, which shows every derivation; the figures are the same ones that page cites, because both are generated from one catalogue.

A model “fits” here when its weight file, the runtime reservation and at least 1 GB of cache all sit on the card. A model that is technically resident but cannot hold a useful prompt is not a fit.

Context a card can hold, once weights and runtime are placed

Derived here
\[ L_{\max} \;=\; \left\lfloor \frac{V_{\text{tot}} - S_{w} - V_{\text{rt}}}{2\,n_{\ell}\,n_{kv}\,d_{h}\,n_{\text{seq}}\,b_{kv}} \right\rfloor \]

The window a model page advertises is what its weights were trained to attend over. This is what your hardware can allocate, which is the number that constrains your work.

  1. Autoregressive attention caches one key vector and one value vector per token per layer, so one token of context costs \( 2\,n_{\ell}\,n_{kv}\,d_{h}\,b_{kv} \) bytes, times \( n_{\text{seq}} \) for concurrent sequences that each keep their own cache.
  2. The cache shares the device with the weights \( S_{w} \) and the runtime's own allocations \( V_{\text{rt}} \), so the bytes available to it are \( V_{\text{tot}} - S_{w} - V_{\text{rt}} \).
  3. Divide the remainder by the per-token cost and take the floor, since a partial token cannot be cached.
  4. Treat the result as an upper bound. Allocators fragment, and on Windows the display driver can page VRAM out from under the runtime.
  5. Each step above is worked in full, with the intermediate forms, on the model selection page.
Symbols in the context-budget relation. Read the architectural quantities from ollama show <tag>; the defaults below are a plausible shape for a 30B-class model and are not a measurement.
SymbolMeaningUnit
\(L_{\max}\)Largest context that fits once weights and runtime are placedtoken
\(V_{\text{tot}}\)Total device memory on the acceleratorB
\(S_{w}\)Weight footprint, the size the model tag listsB
\(V_{\text{rt}}\)Runtime, driver and compute-buffer reservationB
\(n_{\ell}\)Transformer layersdimensionless
\(n_{kv}\)Key/value heads per layerdimensionless
\(d_{h}\)Head dimensiondimensionless
\(n_{\text{seq}}\)Concurrent sequences, --parallel or OLLAMA_NUM_PARALLELdimensionless
\(b_{kv}\)Bytes per cached element, set by OLLAMA_KV_CACHE_TYPEB

The bandwidth cliff is the thing this is protecting you from. If the result is negative, the weights do not fit and llama.cpp or Ollama will place some layers in system RAM. The same weight set streams roughly nine times slower from system RAM than from VRAM, so a smaller model fully resident beats a larger one that spills — essentially always. Confirm residency with ollama ps rather than assuming it.

Offline by design

Every page in the set opens from a local disk with no network access. KaTeX[31] is vendored into assets/katex/ rather than loaded from a content-delivery network — it has no dependencies and is designed to be bundled with a site's own resources — and nothing in the set uses browser storage — so the pages also render correctly inside a sandboxed frame, where storage access throws. The theme follows the operating-system preference and can be overridden for the current page view.

Files you will need that are not in the repository

Installers specific to your hardware — CUDA, the Vulkan SDK, OpenSSL, Docker Desktop, Grafana and the Prometheus executables — are not in the repository. The downloads page lists each with its original creator's download link, and matches Files_you_Will_need_that_areNot_here.txt[32].

Sandboxed prompt access

Giving a sandboxed agent access to local mamba environments

The Open WebUI backends contain code by putting it in a container. The other approach keeps the work on the real filesystem and draws the boundary at the operating system, around each shell command. That is the model to use when an agent must build against the environments, drivers and instrument libraries you already have, and it is configured differently.

Setting names, defaults and behavioural statements are quoted from the Claude Code sandboxing and permissions documentation cited inline and read on 2026-10-18. Where the documentation does not state something, this page says so rather than guessing.

1. What the sandbox actually restricts

The documentation describes the Bash sandbox as "a boundary that the operating system enforces around the shell commands" the agent runs, covering the commands and the processes they start, and notes that because the operating system applies the limits while a command runs, sandboxed commands can run without approving each one[21].

The three dimensions the sandbox restricts, with the documented default reach and the settings key that adjusts it. Reach and key names are quoted from the sandboxing documentation.
DimensionDefault reachSettings keys
Writes "The working directory, a per-user temp directory, and directories you've added" with --add-dir, /add-dir or permissions.additionalDirectories[23]. Protected paths stay write-denied sandbox.filesystem.allowWrite, sandbox.filesystem.denyWrite
Reads "Most of the machine, including credential files such as ~/.ssh and ~/.aws/credentials" sandbox.filesystem.denyRead, sandbox.credentials
Network "No direct route out. Connections go through a proxy on your machine that checks each host against your allowed domains, which start empty" sandbox.network.allowedDomains, sandbox.network.deniedDomains

Reads are permissive by default and writes are not. This asymmetry is the single most important property to internalise. Out of the box a sandboxed command can read most of the machine, credential files included, while it can only write to the working directory and temp. So the configuration effort goes into restricting reads and granting the few extra writes a build needs — not the other way round.

1.1 What runs outside the boundary

The sandbox covers shell commands only. The documentation states that the agent's file tools, MCP servers and hooks run outside it, and specifically that a denyRead entry does not stop the Read tool and allowedDomains does not limit a web-fetch tool[21].

Consequence for a secret you care about. A denyRead rule on a credentials file stops a cat in the shell but not the agent's own file-reading tool. Filesystem permission rules are the other half of that fence, and the documentation also offers permissions.blockReadsOutsideWorkingDirectories as a single switch for denying sandboxed commands read access to home directories and mounted volumes while keeping working directories readable[21][22]. The permission-rule syntax those rules use is documented separately from the sandbox keys[23], which is worth knowing because the two use different path conventions — see §4.4.

2. How it compares to the container backends

Two containment models for the same job, with the property that should decide between them. Container-side facts are from the Open WebUI documentation; sandbox-side facts are from the Claude Code sandboxing documentation.
PropertyContainer backend (Open Terminal, Jupyter)OS-enforced command sandbox
Where code runsInside a container or a separate kernel process[3]On the real filesystem, under OS policy[21]
Sees host mamba environmentsNo, unless rebuilt inside or reached through a host kernelYes, directly
Sees host instrument drivers and licencesNo, without device passthroughYes
Boundary granularityThe whole containerPer command, per path, per domain
Network defaultUnrestricted unless allowed-domains is set[6]Closed. Allowed domains "start empty"[21]
Read defaultContainer filesystem onlyMost of the machine[21]
Blast radius of a mistakeBounded by the containerBounded by the policy you wrote
ReproducibilityHigh: the image is the specificationLower: depends on host state

Choose by what the build needs to touch. If the work can be reproduced from a YAML environment specification, the container is better: reproducible, disposable, and a bounded blast radius whatever the policy says. If the work needs the host — a VISA driver talking to an instrument, a licensed solver, a card that is already configured — the container cannot reach it and the OS-enforced sandbox is the option that can.

3. Turning it on

The documented minimal form is a sandbox block in settings.json[21]. Every key used on this page is listed in the settings reference[22], which is the place to check a default before relying on it.

~/.claude/settings.json — minimal

{
  "sandbox": {
    "enabled": true
  }
}

There is also a one-shot CLI form for testing a policy without editing a file, quoted from the documentation:

claude --settings '{"sandbox": {"enabled": true, "allowUnsandboxedCommands": false}}'

3.1 Two modes

The documentation describes two sandbox modes in which the filesystem and network restrictions are identical, differing only in whether sandboxed commands are auto-approved or require explicit permission[21]. Auto-allow is the mode that makes an unattended build loop practical; regular permissions keeps a prompt in front of every command.

Sandbox modes and the settings that constrain how far a command can escape them.
SettingEffect
allowUnsandboxedCommandsWhether a command that fails under the sandbox may be retried unsandboxed. Setting it to false makes the dangerouslyDisableSandbox parameter ignored entirely[21]
failIfUnavailablePrevents running commands unsandboxed when the sandbox cannot start. The documentation notes the overrides panel shows this as Strict sandbox mode[21]
excludedCommandsCommand patterns that run outside the sandbox altogether — no filesystem restrictions, no network proxy. Covered in §6

For an unattended loop, set both of the first two: allowUnsandboxedCommands: false so a failing command cannot quietly escape, and failIfUnavailable so a sandbox that will not start stops the work rather than running it unconfined.

3.2 Confirming it is actually on

The documentation gives a direct check: switch to manual mode and ask for a command that changes something. The permission prompt for a command running outside the boundary is titled "Bash command (unsandboxed)"[21]. If that title appears for a command you expected to be sandboxed, an excludedCommands pattern is matching it.

4. Granting access to a mamba environment

This is the specific problem. A build needs to read the environment's interpreter and libraries, and to write in three places: the project, the build tree, and wherever the package cache lives.

4.1 What a mamba build touches

Paths a mamba-based build reads or writes, and how each is handled under the sandbox. Default-reach statements are from the sandboxing documentation; the mamba directory names follow this deployment's own configuration.
PathAccessAlready covered?Action
Project sourceRead + writeYes — the working directory is writable by defaultNone
Build tree under the projectRead + writeYesNone
Environment prefix, e.g. [your-envs-dir]/Py3p12Read + executeYes — reads reach most of the machine by defaultNone for reading. Needed only if the agent must install into the environment
Package cache, CONDA_PKGS_DIRSWriteNoAdd to allowWrite, but only if installs are permitted
Environment prefix, for installsWriteNoAdd to allowWrite — and think first (see below)
~/.condarc / ~/.mambarcReadYesNone
Temp directoryWriteYes — a per-user temp directory is writable by defaultNone

The common case needs no filesystem configuration at all. Reading an environment and building inside the project are both covered by the defaults. Configuration is only required when the agent must mutate the environment, and that is a decision worth making deliberately rather than by default — an agent that can write into a shared environment prefix can break every other project that uses it.

4.2 Read-only environment: the recommended posture

The agent runs in the environment and never changes it. Dependency changes go through the YAML specification and a human.

<project>/.claude/settings.json

{
  "sandbox": {
    "enabled": true,
    "allowUnsandboxedCommands": false,
    "filesystem": {
      // "." resolves to the project root when the configuration lives in
      // project settings, which is the documented behaviour. The working
      // directory is writable by default; this is explicit for clarity.
      "allowWrite": ["."]
    },
    "network": {
      // Allowed domains start empty, so an offline build needs nothing here.
      "allowedDomains": []
    }
  }
}

Standardise the invocation, for the same reason as in the container case: a bare python finds the system interpreter.

# Correct: stateless, explicit about the environment.
mamba run -n Py3p12 python -m pytest -q

# Also correct, and the most explicit of all.
[your-envs-dir]/Py3p12/bin/python -m pytest -q      # POSIX
[your-envs-dir]\Py3p12\python.exe -m pytest -q      # Windows

# Wrong inside a sandbox: activation needs a shell hook and each command
# may run in a fresh shell.
mamba activate Py3p12 && pytest

4.3 Mutable environment, when the agent must install

Sometimes the task is adding a dependency. Grant the two write paths explicitly. The documentation notes these paths are enforced at the OS level so all commands inside the sandbox, child processes included, respect them, and recommends this over excluding the tool from the sandbox entirely[21].

~/.claude/settings.json — environment writes permitted

{
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "allowWrite": [
        // The environment prefix the agent may modify. Name ONE environment,
        // never the whole envs directory: a wider entry lets a task for one
        // project break another project's environment.
        "~/miniforge3/envs/ai_sandbox",
        // The package cache. Without it a solve downloads and then fails to
        // write, which presents as a confusing permission error.
        "~/miniforge3/pkgs"
      ],
      "denyWrite": [
        // Belt and braces: the base environment stays immutable even though
        // the allowWrite entries above do not include it.
        "~/miniforge3/envs/base"
      ]
    },
    "network": {
      "allowedDomains": ["conda.anaconda.org", "repo.anaconda.com", "pypi.org", "files.pythonhosted.org"]
    }
  }
}

Create a dedicated environment for this. Clone the real environment once, grant write access only to the clone, and let the agent install into it. The clone is disposable, nothing else depends on it, and a bad solve costs a mamba env create rather than a day:

mamba env create -f Py3p12_Clean.yml -n ai_sandbox

The -f and -n flags are documented in the conda command reference as "Environment definition file" and "Name of environment"[24].

4.4 How overlapping path rules resolve

The documentation states that when read rules overlap, the rule with the narrower path applies, and gives three cases[21]. The third is the one that matters for secrets.

Overlap resolution for read rules, quoted from the sandboxing documentation, with the consequence for a mamba layout.
RulesDocumented resultUse for
denyRead: ["~/"] "~/projects is readable and the rest of the home directory stays blocked. The narrower allow re-opens that part of the denied region" Blocking the home directory while keeping the environments and the project readable
allowRead: ["~/"] "~/.env stays blocked and the rest of the home directory is readable. The deny holds inside a wider allow, so a broad allow can't silently re-expose a secret" Carving one file out of a broad allow
allowRead: ["~/"] "Every .env under the home directory stays blocked and the rest is readable" Wildcard denies. The form to use for secrets scattered across many project directories

Note also that the path convention here differs from the permission-rule convention. The documentation states sandbox filesystem paths use standard conventions — /tmp/build absolute, ~/.kube home-relative — which "differs from Read and Edit permission rules", where //path is absolute and /path is project-relative[21][23]. Two conventions in two adjacent settings blocks is a reliable source of rules that silently never match.

When the same filesystem array appears in several settings scopes they are merged rather than replaced, and an edit during a session is applied to the running session, so the next sandboxed command runs under the new paths[21]. That makes it practical to widen a path mid-task without restarting.

5. Network policy for package installs

Allowed domains start empty and connections go through a proxy on the machine that checks each host[21]. So a sandboxed build is offline until told otherwise, which is the right default and also the first thing that appears broken.

Minimum allowed-domain sets by task. Keep the list as short as the task allows; an entry is a permanent hole in an otherwise closed egress policy.
TaskDomains
Build and test only, no installsempty — the default, and the right answer for most work
conda / mamba installsconda.anaconda.org, repo.anaconda.com
conda-forge specificallyconda.anaconda.org (conda-forge is a channel on that host)
pip installspypi.org, files.pythonhosted.org
Cloning a dependencygithub.com, codeload.github.com
Pulling a local modelNothing. Ollama is on the LAN, not the internet

Local services are reached by address, not by domain. The inference host in this deployment is 192.168.7.27:11434. The documentation notes the bracketed form for a literal address in network.allowedDomains, for example "[::1]"[21]. Confirm with a probe rather than assuming a LAN address is exempt from the proxy.

When a connection is blocked the documentation states the denied host is named in the command's result, so the agent can see what was blocked and may retry with the unsandboxed parameter[21]. That is a useful diagnostic and a reason to set allowUnsandboxedCommands: false: the agent should report the blocked host, not route around the policy.

6. When a tool cannot work inside the sandbox

sandbox.excludedCommands runs matching commands outside the boundary — "no filesystem restrictions and no network proxy" — and the documentation is explicit that a tool needing one more directory or one more host should get allowWrite or allowedDomains instead, which keeps the command sandboxed[21].

~/.claude/settings.json — the documented example

{
  "sandbox": {
    "enabled": true,
    "excludedCommands": ["docker compose *"]
  }
}

6.1 The matching rules, and why a pattern misses

Five rules from the documentation decide whether a call leaves the sandbox[21]. Each one is a way for a pattern to behave unexpectedly.

Matching rules for excludedCommands, quoted from the sandboxing documentation, with the practical consequence.
RuleConsequence
"End the pattern with *" — a pattern with no wildcard is an exact match, so docker matches only docker with no argumentsA pattern without the trailing wildcard almost never matches a real call
"Every command in the call has to match": npm ci && docker compose build stays sandboxed unless another entry covers npm ciChained commands are all-or-nothing
Matching is on the text of the call, so "a script or make target that calls docker internally doesn't match, and neither does /usr/local/bin/docker"An absolute path or a wrapper script defeats the pattern. This is usually what you want
"Some calls stay sandboxed": a redirect to a file, a cd, or a command substitution such as $(...) keeps the whole call sandboxedA build wrapped in cd build && ... never leaves the sandbox
Where the entry is saved can matter: under an admin-required sandbox, entries in a repository's .claude/settings.json and .claude/settings.local.json are ignoredA repository cannot widen a managed policy

The documented warning, which applies directly to a build. An excluded command runs with your full access, and a broad entry such as docker * covers everything that tool can do. The documentation adds that a pattern covering "an interpreter, a script inside your working directory, or a tool that acts on a file there, as docker compose does with its compose file" lets the agent write that file and then run it outside the sandbox[21].

A build script is exactly that shape. Excluding cmake * or ./build.sh * hands the agent an unsandboxed interpreter for a file it can rewrite, which removes the boundary entirely. Grant the directory or the host with allowWrite or allowedDomains instead.

6.2 Disabling filesystem isolation while keeping network isolation

sandbox.filesystem.disabled set to true skips filesystem isolation while keeping network isolation, which the documentation describes as the right choice "when you sandbox to control where commands connect rather than what they write"[21].

{
  "sandbox": {
    "enabled": true,
    "filesystem": { "disabled": true },
    "network": { "allowedDomains": ["conda.anaconda.org", "pypi.org", "files.pythonhosted.org"] }
  }
}

The documented escalation path. With filesystem isolation off and commands auto-allowed, the documentation warns that a sandboxed command can write files later commands run or read — "shell startup files, executables on $PATH, or ~/.claude/settings.json" — and use them to widen its own access on the next run[21]. Set this only for workloads trusted not to escalate. For a build against a shared mamba installation, the narrow allowWrite list in §4.3 is the safer configuration and costs two lines.

7. Keeping credentials out of reach

Because reads reach most of the machine by default, credentials need explicit handling. sandbox.credentials takes files and envVars entries, and for "mode": "deny" the documentation states file paths are denied for reads inside the sandbox and environment variables are unset before each sandboxed command runs[21].

~/.claude/settings.json — the documented form

{
  "sandbox": {
    "enabled": true,
    "credentials": {
      "files": [
        { "path": "~/.aws/credentials", "mode": "deny" },
        { "path": "~/.ssh", "mode": "deny" }
      ],
      "envVars": [
        { "name": "GITHUB_TOKEN", "mode": "deny" },
        { "name": "NPM_TOKEN", "mode": "deny" }
      ]
    }
  }
}

Three documented properties worth knowing before relying on this[21]:

  • There is no built-in deny list. "Only the files and variables you list are restricted." Nothing is protected by default.
  • deny entries merge across scopes and only ever narrow. Any scope can add one and no scope can remove one another scope added.
  • File denial is part of the filesystem layer. It does not apply if filesystem isolation is disabled, although environment-variable protection still does.

For this deployment, the list to write. A government-contracting and instrumentation workstation has credentials an agent has no business reading: SAM.gov and Costpoint session material, instrument licence files, VPN profiles, signing keys. These are not in any default deny list because there is no default deny list. Enumerate them once, as deny entries in user settings so no project scope can relax them.

8. A worked configuration for this deployment

Two files. User settings carry the restrictions that must hold everywhere; project settings carry the grants a particular build needs.

~/.claude/settings.json — restrictions that always apply

{
  "sandbox": {
    "enabled": true,

    // No quiet escape: a command that fails under the sandbox must report the
    // failure rather than being retried with full access.
    "allowUnsandboxedCommands": false,

    // If the sandbox itself cannot start, stop rather than running unconfined.
    "failIfUnavailable": true,

    "filesystem": {
      // Deny the home directory wholesale, then re-open only what a build
      // legitimately reads. The documented overlap rule is that the narrower
      // allow re-opens that part of the denied region.
      "denyRead": [
        "~/",
        // A wildcard deny holds inside a wider allow the same way an exact
        // path does, so this survives the allowRead entries below.
        "~/**/.env",
        "~/**/*.pem",
        "~/**/id_rsa*"
      ],
      "allowRead": [
        "~/miniforge3",          // interpreters and libraries
        "~/projects",            // source trees
        "~/.condarc",            // channel configuration
        "~/.mambarc"
      ],
      "denyWrite": [
        "~/miniforge3/envs/base" // the base environment is never a target
      ]
    },

    "credentials": {
      "files": [
        { "path": "~/.ssh", "mode": "deny" },
        { "path": "~/.aws/credentials", "mode": "deny" },
        { "path": "~/.config/gh", "mode": "deny" }
      ],
      "envVars": [
        { "name": "GITHUB_TOKEN", "mode": "deny" },
        { "name": "GH_TOKEN", "mode": "deny" }
      ]
    },

    "network": {
      // Empty by default. A project that needs installs opens the specific
      // hosts in its own settings file.
      "allowedDomains": []
    }
  }
}

<project>/.claude/settings.json — grants for one project

{
  "sandbox": {
    "enabled": true,
    "filesystem": {
      // "." resolves to the project root in project settings. Arrays merge
      // across scopes, so these add to the user-level rules above rather
      // than replacing them.
      "allowWrite": [
        ".",
        "/tmp/cmake-build"
      ],
      "allowRead": ["."]
    },
    "network": {
      // This project pulls dependencies, so the indexes are opened here and
      // nowhere else.
      "allowedDomains": [
        "conda.anaconda.org",
        "repo.anaconda.com",
        "pypi.org",
        "files.pythonhosted.org"
      ]
    }
  }
}

Checks 4 through 7 are the ones to actually run. A policy that has never been tested against a denial is a policy you are assuming, and the asymmetric read default means an untested configuration usually fails open rather than closed.

9. Platform limits

Platform support for the OS-enforced sandbox, quoted from the sandboxing documentation. The Windows row matters for this deployment, where the nodes are Windows hosts.
PlatformDocumented behaviour
macOSSupported
LinuxSupported. Needs socat, described as "the relay used to route network traffic through the sandbox proxy"[21]
WSL2Supported, with the same Linux prerequisites
Native WindowsCommands run unsandboxed. The documentation states that to use the sandbox on a Windows machine, run inside a WSL2 distribution[21]

Read this before configuring anything on a Windows node. On native Windows the sandbox does not apply and commands run unsandboxed. A settings.json full of careful deny rules has no effect there. The nodes in this deployment are Windows hosts, so the practical options are: run the agent inside WSL2 and keep the project on the Linux filesystem, or use the container backends on the build and test page, which contain by deployment rather than by OS policy.

On WSL2 there is one more documented subtlety. WSL hands a launch of a Windows binary — cmd.exe, powershell.exe, anything under /mnt/c/ — to the Windows host over a Unix socket, so whether a sandboxed command can launch one follows the sandbox's Unix-socket settings, and an optional seccomp filter has to be installed to block the socket at all[21]. A build that shells out to cl.exe on the Windows side is therefore crossing the boundary, and allowAllUnixSockets — which the documentation notes "opens every Unix socket to sandboxed commands" — is the setting that permits it. Keep the toolchain on one side of that line.

10. Running both models side by side

The two approaches are complementary, and a project can use both against the same source tree.

Task-to-backend assignment for a project that uses both containment models. The deciding question is always whether the task needs the host.
TaskBackendBecause
Refactor pure-Python computationOpen Terminal containerReproducible, disposable, no host access needed
Build and test a C++ extensionOpen Terminal containerThe toolchain is in the image; the blast radius is the container
Debug a Qt GUI against a real displayOS-enforced sandbox on the hostA container has no display
Exercise an instrument driver over VISAOS-enforced sandbox on the hostThe hardware is on the host
Reduce data into Veusz .vszh5 outputEitherThe artefact is a file, so it works in both
Rebuild llama.cpp with CUDA and VulkanOS-enforced sandbox on the hostNeeds the host CUDA toolkit and the real GPU
Anything touching credentialsNeither, without reviewContainer mounts and sandbox deny lists both have to be configured deliberately, and both default to being wrong

One sentence to carry away. The container is the better default because its boundary exists whether or not the policy is right; the OS-enforced sandbox is the one that can reach the host, and its boundary is exactly as good as the rules you wrote and tested. Use the container unless the task needs the host, and when it does, run the denial checks in §8 before letting the agent loose.

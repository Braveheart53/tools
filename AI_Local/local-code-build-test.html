Local software generation & test

Letting a local model build and test code on your own hardware

The rest of this set gets a model answering on your network. This page closes the loop: giving that model a real shell and a real Python environment on a machine you own, so it can write code, compile it, run the tests, read the failures and try again — with nothing leaving the LAN.

Every equation is tagged Stated, Derived here or Measured value, and every one carries an information button that opens a variable table with units. Settings names are quoted verbatim from the vendor documentation listed in References.

1. Which execution backend to use

Open WebUI can run code three ways, and they are not interchangeable. The published documentation marks both of the original Code Interpreter engines as legacy and recommends Open Terminal instead[1].

The three execution backends Open WebUI offers, with the capability that decides between them. Column contents are quoted from the Open WebUI documentation for code execution, the Jupyter integration tutorial and the Open Terminal pages.
BackendWhere code runsCan install packagesShell / compilerPer-user isolationStatus
Pyodide The reader's browser, as WebAssembly No. A fixed package set loads on demand and the model cannot add to it[1] None Browser sandbox Legacy; documented as possibly deprecated[1]
Jupyter engine A Jupyter server you run Yes, whatever that kernel's environment allows Through the kernel, so subprocess and ! magics reach the host shell None by default. The documentation advises against it for multi-tenant production[3] Legacy[1]
Open Terminal A Docker container, or bare metal on the host Yes, including system packages, git and ffmpeg[3] A full Linux shell; Windows is supported on bare metal through pywinpty[4] Per-user workspaces through the separate Terminals orchestrator[3] Recommended[3]

Recommendation for this deployment. Use Open Terminal in Docker as the default, because it is the only backend that can run a compiler, and it is the one the vendor documentation points at. Keep the Jupyter engine alongside it for the specific case covered in §4: driving a named mamba environment that already exists on the host, with your instrument drivers, PySide6 and Veusz already solved. Leave Pyodide on only as a fallback for a reader with no backend at all.

One point that catches people out: CODE_INTERPRETER_BLOCKED_MODULES exists but the documentation states plainly that it "is not a security boundary" and only blocks direct top-level imports[1]. Treat it as a guard rail against accidents, never as a containment mechanism.

2. Where each piece runs

The four-node layout in the rest of this set has NODE-A as the inference host at 192.168.7.27, with RPC workers at .28, .45 and .181[32]. The execution backend does not have to live on the inference host, and there is a good argument for separating them: a build that saturates sixteen cores and twenty gigabytes of RAM will evict a resident model from page cache and stall token generation for every other user on the network.

3. Open Terminal: the recommended backend

3.1 Run the container

The documented Docker invocation is below. The volume at /home/user is what makes a workspace survive a container restart[4].

PowerShell, on the host that will run builds

# Open Terminal, with an explicit API key so it is reproducible.
# If OPEN_TERMINAL_API_KEY is omitted a key is generated and printed to the
# container log, which you would then have to read back with docker logs.
docker run -d `
  --name open-terminal `
  --restart unless-stopped `
  -p 8000:8000 `
  -v open-terminal:/home/user `
  -e OPEN_TERMINAL_API_KEY=replace-with-a-long-random-string `
  ghcr.io/open-webui/open-terminal

# Confirm the API is up. The documented check is the interactive API page.
# Expect the Open Terminal API documentation to render.
Start-Process http://localhost:8000/docs

Verify the service from inside the Open WebUI container, which is the check the connection guide gives. A working connection prints {"status": "ok"}[5].

docker exec open-webui curl -s http://open-terminal:8000/health

3.2 Pre-install the toolchain the model will need

Three Docker-only variables install packages at container start. The documentation notes that these reinstall on every container start, so a long list costs start-up time[6].

Open Terminal package-installation variables, which apply to the Docker image only, with the values this deployment uses for C++ and Python work.
VariableInstallsValue used here
OPEN_TERMINAL_PACKAGESSystem packagesbuild-essential cmake ninja-build git pkg-config
OPEN_TERMINAL_PIP_PACKAGESPython packagespytest numpy scipy h5py
OPEN_TERMINAL_NPM_PACKAGESnpm packagesunset

Prefer a derived image for anything substantial. Because the package variables reinstall on every start, a toolchain of any size belongs in a Dockerfile that starts FROM ghcr.io/open-webui/open-terminal. Keep the variables for one or two late additions.

3.3 Constrain it

Four configuration settings matter before this is pointed at a model. The precedence order is built-in defaults, then /etc/open-terminal/config.toml, then ~/.config/open-terminal/config.toml, then OPEN_TERMINAL_* environment variables, then CLI flags[6].

Open Terminal settings with a direct bearing on blast radius, with the documented default and the value recommended for a home network.
SettingDefaultRecommendedWhy
OPEN_TERMINAL_ALLOWED_DOMAINSNoneYour package indexes onlyDocumented as an egress firewall: "only allow outbound connections to these domains"[6]. Unset means unrestricted egress
OPEN_TERMINAL_CORS_ALLOWED_ORIGINS*Your Open WebUI originA start-up warning is emitted when it is unset[6]
OPEN_TERMINAL_EXECUTE_TIMEOUTUnsetLonger than your slowest clean buildSeconds to wait for command output[6]. Unset plus a 40-minute build is an agent that appears to hang
OPEN_TERMINAL_FILE_BROWSER_ROOThome/workspaceAccepts home, an explicit path, or filesystem[6]. filesystem exposes the whole container
OPEN_TERMINAL_MAX_SESSIONS162–4 for a single userCaps concurrent terminal sessions[6], which also caps how many builds can be started at once

OPEN_TERMINAL_EXECUTE_DESCRIPTION is worth setting as well. It is documented as "custom text telling the AI about installed tools"[6], and it is the cheapest way to stop a model trying to apt-get install a compiler that is already present.

3.4 Connect it to Open WebUI

The connection steps are specific, and the documentation warns against the wrong panel: adding it under "External Tools" or "Tool Servers" skips the built-in file browser and terminal sidebar[5].

  1. Click your name at the bottom of the left sidebar, then Settings.
  2. Go to Admin → Integrations, not the personal Integrations entry. The Open Terminal section is greyed out if ENABLE_TOOL_SERVERS is False[5].
  3. In the Open Terminal section, click + and enter the URL and API key. Leave Auth Type as Bearer.
  4. Save, and confirm the toggle is on. Optionally restrict the connection to a group with the access-control button.
  5. In Workspace → Models, edit your model and set Function Calling to Native, which is the default as of v0.10.0. Legacy mode uses prompt-based tool calling and may not trigger terminal commands at all[5].
  6. In a chat, click the terminal button and select the terminal under System.

4. The Jupyter engine, for a mamba environment you already own

Open Terminal is the better default, but it cannot see the host's mamba environments. When the point of the exercise is to run code against an environment that already has PySide6, Veusz, h5py and instrument drivers resolved — the Py3p12 environments in this repository[30] — the Jupyter engine pointed at a kernel in that environment is the shorter path.

4.1 The variables

Twelve variables, from the Jupyter integration tutorial[2]. Three properties of them are easy to get wrong and each one produces a silent failure.

Open WebUI variables for the Jupyter execution backend, with the values for a Jupyter server reachable at host.docker.internal:8888. Names and accepted values are quoted from the Jupyter integration tutorial.
VariableValueNote
ENABLE_CODE_INTERPRETERTrueGlobal toggle, default true[1]
CODE_EXECUTION_ENGINEjupyterThe manual Run button
CODE_EXECUTION_JUPYTER_URLhttp://host.docker.internal:8888—
CODE_EXECUTION_JUPYTER_AUTHtokenAccepts only token or password; any other value sends no credentials at all
CODE_EXECUTION_JUPYTER_AUTH_TOKENyour tokenMust equal Jupyter's JUPYTER_TOKEN
CODE_EXECUTION_JUPYTER_TIMEOUT60Seconds; raise it for anything that compiles
CODE_INTERPRETER_ENGINEjupyterSet this explicitly. It defaults to pyodide and does not inherit from CODE_EXECUTION_ENGINE
CODE_INTERPRETER_JUPYTER_URLsame as aboveDefaults to its CODE_EXECUTION_* counterpart
CODE_INTERPRETER_JUPYTER_AUTHtokenDefaults to its counterpart
CODE_INTERPRETER_JUPYTER_AUTH_TOKENyour tokenDefaults to its counterpart
CODE_INTERPRETER_JUPYTER_TIMEOUT60Defaults to its counterpart
ENABLE_ORJSONTrueOn by default; speeds output on the Jupyter engine. Read at start-up, so restart after changing it

Three traps, each of which fails silently.

1. The engine variable does not inherit. CODE_INTERPRETER_ENGINE defaults to pyodide regardless of CODE_EXECUTION_ENGINE. Set both, or the model keeps running code in the browser while the manual Run button uses Jupyter, and the symptom is a model that cannot see files it just wrote.

2. These are persisted settings. An environment variable takes effect only on the first start with a fresh database; after that the saved value wins unless ENABLE_PERSISTENT_CONFIG=False[2]. On an existing install, change the values in Settings → Admin → Code Execution, not in docker run. ENABLE_PERSISTENT_CONFIG is documented as controlling "whether the system prioritizes configuration saved in the database over environment variables"[7].

3. The auth value is strict. Anything other than token or password sends no credentials, which presents as a connection that fails without a useful error.

4.2 Kernel lifetime, and what that means for a build

The tutorial states that each run uses a fresh kernel which is deleted afterwards: variables do not persist between runs, but files written to disk do[2]. That single property dictates how the model has to work.

Consequences of per-run kernel disposal for a write-build-test loop on the Jupyter engine.
ConsequenceWhat to do about it
An object built in step 1 is gone by step 2Persist state to disk between steps. HDF5 through h5py, or a pickle, is the natural choice for numeric work
A sys.path edit does not carry forwardInstall the package under test in editable mode once, from the shell, rather than patching the path per run
A compile in step 1 and a link in step 2 share only the filesystemKeep the whole build inside one cell, driven by subprocess.run, so it succeeds or fails as a unit
Long builds hit the timeoutRaise both *_JUPYTER_TIMEOUT values above the slowest clean build, or fire the build off and poll a log file

The Jupyter engine also uses Jupyter's own filesystem, which means the Open WebUI file browser and the /mnt/uploads/ path are unavailable[1]. Files have to be moved in and out through the Jupyter work directory.

5. Wiring a named mamba environment into the sandbox

This deployment's Python work lives in mamba environments created from YAML, with CONDA_ENVS_DIRS pointing at a chosen directory[30]. Two routes expose such an environment to a model, and the choice follows from whether the environment must stay on the host.

5.1 Route A: environment on the host, reached through a Jupyter kernel

Register the environment as a named Jupyter kernel, then point the Jupyter engine at that server. Kernel registration is a one-time step per environment.

PowerShell, on the host holding the environment

# 1. Install the kernel machinery and the test runner INTO the target
#    environment. -n selects the environment by name; conda env create
#    documents -n/--name as "Name of environment".
mamba install -n Py3p12 ipykernel jupyter_server pytest -y

# 2. Register the environment as a Jupyter kernel. The --name is the kernel
#    id used in API calls; --display-name is what a human sees in a picker.
mamba run -n Py3p12 python -m ipykernel install --user `
  --name py3p12 `
  --display-name "Python 3.12 (Py3p12 mamba)"

# 3. Confirm it registered.
mamba run -n Py3p12 jupyter kernelspec list

PowerShell — start the server Open WebUI will talk to

# ServerApp.ip and ServerApp.open_browser are the documented public-server
# options [29]; JUPYTER_TOKEN is the variable the Open WebUI tutorial sets on
# the Jupyter container [2], and it must match CODE_*_JUPYTER_AUTH_TOKEN.
$env:JUPYTER_TOKEN = "replace-with-a-long-random-string"

mamba run -n Py3p12 jupyter server `
  --ServerApp.ip='0.0.0.0' `
  --ServerApp.port=8888 `
  --ServerApp.open_browser=False `
  --ServerApp.root_dir="C:\ai_workspace"

The Jupyter Server documentation gives c.ServerApp.ip = '*' as the way to "bind on all interfaces (ips) for the public server" and c.ServerApp.open_browser = False alongside it[29]; 0.0.0.0 is used above because it is the form the Open WebUI container resolves against. The token is supplied through JUPYTER_TOKEN, which is the variable the Open WebUI integration tutorial sets[2], and it must equal the CODE_*_JUPYTER_AUTH_TOKEN values from §4.1.

Bind deliberately. 0.0.0.0 is required for the Open WebUI container to reach the server, and it also exposes the kernel to everything that can route to the host. Pair it with a firewall rule that admits only the Open WebUI host, in the same style as the rules already defined for this deployment: -RemoteAddress 192.168.7.27 rather than the whole subnet.

Run it as a service with NSSM, exactly as the other services in this set are run, so it survives a reboot:

C:\tools\nssm.exe install JupyterCodeEval `
  "C:\Users\<you>\miniforge3\envs\Py3p12\Scripts\jupyter.exe" `
  "server --ServerApp.ip=0.0.0.0 --ServerApp.port=8888 --ServerApp.open_browser=False --ServerApp.root_dir=C:\ai_workspace"

C:\tools\nssm.exe set JupyterCodeEval AppEnvironmentExtra JUPYTER_TOKEN=replace-with-a-long-random-string
C:\tools\nssm.exe set JupyterCodeEval Start SERVICE_AUTO_START
C:\tools\nssm.exe set JupyterCodeEval AppStdout C:\logs\jupyter-codeeval.log
C:\tools\nssm.exe set JupyterCodeEval AppStderr C:\logs\jupyter-codeeval-err.log
Start-Service JupyterCodeEval

5.2 Route B: environment rebuilt inside Open Terminal

Keeps the host clean and gives the model a compiler. The environment is reproduced from the same YAML, so the two routes stay in step.

Dockerfile — Open Terminal with micromamba

FROM ghcr.io/open-webui/open-terminal

# Build toolchain. Installed in the image rather than through
# OPEN_TERMINAL_PACKAGES, because that variable reinstalls on every start.
USER root
RUN apt-get update \
 && apt-get install -y --no-install-recommends \
      build-essential cmake ninja-build git ca-certificates bzip2 curl \
 && rm -rf /var/lib/apt/lists/*

# micromamba: a single static binary, no shell initialisation needed.
ENV MAMBA_ROOT_PREFIX=/opt/micromamba
RUN mkdir -p /opt/micromamba \
 && curl -Ls https://micro.mamba.pm/api/micromamba/linux-64/latest \
      | tar -xvj -C /usr/local bin/micromamba

# Create the environment from the project's own YAML, so the container and
# the host resolve the same specification.
COPY Py3p12_Clean.yml /tmp/Py3p12_Clean.yml
RUN micromamba create -y -n Py3p12 -f /tmp/Py3p12_Clean.yml \
 && micromamba clean --all --yes

# Tell the model what it has, so it does not try to install a compiler.
ENV OPEN_TERMINAL_EXECUTE_DESCRIPTION="Debian with build-essential, cmake and ninja. Python lives in the micromamba environment 'Py3p12'; run Python as: micromamba run -n Py3p12 python ..."
ENV OPEN_TERMINAL_FILE_BROWSER_ROOT=/workspace

RUN mkdir -p /workspace && chown -R user:user /workspace
USER user
WORKDIR /workspace

5.3 The invocation that matters

Inside a sandbox, mamba activate is the wrong tool. Activation requires a shell hook, and each command the model issues may run in a fresh shell. run is the documented alternative; the micromamba user guide gives micromamba run -p /tmp/env pytest myproject/tests and notes it is useful in CI and Docker environments, "where running shell activation hooks is complicated"[25].

Environment invocation forms, and which to put in a model's system prompt. The -n/-p/-f flags are documented in the conda command reference and the micromamba user guide.
FormBehaviourUse in a sandbox
mamba activate Py3p12Mutates the current shell; needs the shell hook installedNo. Fails or silently no-ops in a fresh shell
mamba run -n Py3p12 <cmd>Runs one command with the environment appliedYes. Stateless and the form to standardise on
micromamba run -p /opt/envs/Py3p12 <cmd>Same, selecting by full prefix pathYes, when the environment is outside the configured envs_dirs
/opt/envs/Py3p12/bin/pythonCalls the interpreter directlyWorks, and is the most explicit. Misses environment variables an activation script would set
mamba env create -f env.yml -n Py3p12Creates from a YAML specification[24]Setup only, not per task

Put the form in the system prompt. A model given a bare shell will reach for python and get the container's system interpreter, then report that PySide6 is not installed. One sentence in OPEN_TERMINAL_EXECUTE_DESCRIPTION or the model's system prompt — "run Python only as micromamba run -n Py3p12 python" — removes an entire class of wasted iteration.

6. C++ builds: CMake, MSVC and llama.cpp itself

The compiler invocations already recorded for this deployment pass absolute paths to cl.exe and nvcc.exe, with -DCMAKE_CUDA_ARCHITECTURES=61[32]. That is correct for a hand-driven build and poor material for a model: the MSVC toolset version is embedded in the path, so the command breaks after a Visual Studio update, and a model has no way to discover the new one.

6.1 Give the model a script, not a command line

A wrapper script makes the build one call with no arguments to get wrong, and gives a single place to fix a toolchain change.

scripts/build_cpp.ps1 (Windows, MSVC)

<#
.SYNOPSIS
    Configure and build a CMake project with a bounded job count.
.DESCRIPTION
    Written to be called by a model with no arguments. Discovers the MSVC
    toolchain with vswhere rather than hard-coding a toolset version, and
    caps parallelism from available memory so a build cannot evict a
    resident model from RAM.
.NOTES
    Author : William W. Wallace
    Version: 0.0.1
#>
[CmdletBinding()]
param(
    [string]$SourceDir = ".",
    [string]$BuildDir  = "build",
    [ValidateSet("Debug","Release","RelWithDebInfo")]
    [string]$Config    = "Release",
    # 0 means "derive from cores and free memory" (see the equation on this page).
    [int]$Jobs         = 0,
    [double]$MemPerJobGB = 2.0
)

$ErrorActionPreference = "Stop"

# -- Locate the toolchain -------------------------------------------------
# vswhere ships with every VS 2017+ installer at a fixed path, so this is
# stable where a hard-coded MSVC toolset path is not.
$vswhere = "${env:ProgramFiles(x86)}\Microsoft Visual Studio\Installer\vswhere.exe"
if (-not (Test-Path $vswhere)) {
    throw "vswhere not found at $vswhere. Install the VS Build Tools."
}
$vsRoot = & $vswhere -latest -products * `
    -requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64 `
    -property installationPath
if (-not $vsRoot) { throw "No MSVC C++ toolset found by vswhere." }
Write-Host "MSVC toolchain: $vsRoot"

# -- Derive a safe job count ---------------------------------------------
if ($Jobs -le 0) {
    $cores = [Environment]::ProcessorCount
    # FreePhysicalMemory is in KiB; convert to GiB.
    $freeGB = (Get-CimInstance Win32_OperatingSystem).FreePhysicalMemory / 1MB
    $byMem  = [Math]::Floor($freeGB / $MemPerJobGB)
    $Jobs   = [Math]::Max(1, [Math]::Min($cores, $byMem))
    Write-Host ("Jobs: {0} (cores {1}, free {2:N1} GiB at {3} GiB/job)" `
                -f $Jobs, $cores, $freeGB, $MemPerJobGB)
}

# CMAKE_BUILD_PARALLEL_LEVEL is equivalent to passing --parallel, and holds
# even if a nested script invokes the build without the flag.
$env:CMAKE_BUILD_PARALLEL_LEVEL = $Jobs

# -- Configure ------------------------------------------------------------
# Ninja Multi-Config is preferred over the VS generator: it is faster and
# its output is far easier for a model to parse than MSBuild's.
cmake -S $SourceDir -B $BuildDir -G "Ninja Multi-Config"
if ($LASTEXITCODE -ne 0) { throw "CMake configure failed ($LASTEXITCODE)." }

# -- Build ----------------------------------------------------------------
cmake --build $BuildDir --config $Config --parallel $Jobs
if ($LASTEXITCODE -ne 0) { throw "Build failed ($LASTEXITCODE)." }

Write-Host "Build succeeded: $BuildDir ($Config, $Jobs jobs)"

The parallel-level variable is documented as specifying "the maximum number of concurrent processes to use when building using the cmake --build command line Build Tool Mode", and setting it to 8 behaves as if --parallel 8 had been passed[27]. Setting it in the environment rather than only on the command line is what makes the cap survive a nested invocation.

6.2 The job count is a memory question, not a core question

Safe parallel job count for a C++ build

Derived here
\[ j^{\star} \;=\; \min\!\left( n_{\text{cpu}},\; \left\lfloor \frac{M_{\text{avail}}}{M_{\text{job}}} \right\rfloor \right) \]

Relevant because an agent told to "build the project" will reach for -j$(nproc), and on a machine that is simultaneously holding a 19 GB model resident the memory term, not the core count, is the binding constraint. Set CMAKE_BUILD_PARALLEL_LEVEL in the environment so the limit holds regardless of how the build is invoked[28].

  1. Compilation of independent translation units is embarrassingly parallel up to the core count, so \( j \le n_{\text{cpu}} \) is the first bound.
  2. Each concurrent compiler process holds a peak resident set \( M_{\text{job}} \). Heavily templated C++ and link-time optimisation push this well above the 300–500 MB that plain C costs; 1.5–2.5 GB per job is realistic for a template-heavy target.
  3. Exceeding available memory does not fail cleanly. The machine swaps, the build slows by an order of magnitude, and the resident model may be evicted. So \( j \le \lfloor M_{\text{avail}}/M_{\text{job}} \rfloor \) is the second bound.
  4. Take the smaller of the two bounds.
  5. Worked example for a machine running a local coding model. 16 logical cores, 64 GB installed, 19 GB pinned by the model server and 8 GB by the operating system and editor, leaving \( M_{\text{avail}} = 37\ \mathrm{GB} \). At \( M_{\text{job}} = 2\ \mathrm{GB} \): \( \lfloor 37/2 \rfloor = 18 \), so \( j^{\star} = \min(16,\,18) = 16 \).
  6. Same machine with 32 GB installed: \( M_{\text{avail}} = 5\ \mathrm{GB} \), \( \lfloor 5/2 \rfloor = 2 \), and \( j^{\star} = 2 \). The core count is irrelevant.
Symbols in the parallel-job relation. \(M_{\text{avail}}\) is memory free after the model server and the operating system have taken their share, not installed memory.
SymbolMeaningUnit
\(j^{\star}\)Jobs to pass to cmake --build . --parallel or to CMAKE_BUILD_PARALLEL_LEVELdimensionless
\(n_{\text{cpu}}\)Logical cores available to the builddimensionless
\(M_{\text{avail}}\)System memory free with the model server already residentB
\(M_{\text{job}}\)Peak resident set of one compiler processB

Amdahl speed-up of a parallel build

Stated
\[ S(j) \;=\; \frac{1}{(1-p) + \dfrac{p}{j}}, \qquad \lim_{j\to\infty} S(j) \;=\; \frac{1}{1-p} \]

The serial fraction of a native build is the configure step and the final link, and a single-threaded link of a large binary can be tens of seconds. With \( p = 0.85 \) the ceiling is \( S_{\infty} = 6.7 \) no matter how many cores are added, which is worth knowing before an agent is allowed to raise the job count in a loop.

Symbols in Amdahl's relation as applied to a compile-and-link cycle.
SymbolMeaningUnit
\(S(j)\)Speed-up over a single-job builddimensionless
\(p\)Fraction of total build time that parallelises, essentially the compile phasedimensionless
\(j\)Concurrent jobsdimensionless
\(1-p\)Serial fraction: configure, dependency scan, archive and linkdimensionless

6.3 Rebuilding llama.cpp from the sandbox

The CUDA and Vulkan configure line recorded for this deployment, with the absolute compiler paths removed so CMake discovers them[32]:

# Run from a Developer PowerShell, so the MSVC environment is already set
# and CMake needs no explicit CMAKE_C_COMPILER / CMAKE_CXX_COMPILER.
# -DGGML_RPC=ON is what builds rpc-server for the distributed setup.
cmake -S . -B build `
  -G "Ninja Multi-Config" `
  -DGGML_VULKAN=ON `
  -DGGML_CUDA=ON `
  -DGGML_RPC=ON `
  -DGGML_CCACHE=OFF `
  -DCMAKE_CUDA_ARCHITECTURES=61

cmake --build build --config Release --parallel $env:CMAKE_BUILD_PARALLEL_LEVEL

CMAKE_CUDA_ARCHITECTURES=61 is specific to this hardware. 61 is Pascal. A model copying this line onto a different card produces binaries that will not run on it. State the target architecture in the system prompt, or set native and let CMake detect it.

6.4 Making failures legible

A model's iteration count depends almost entirely on how good the error text is, and N_{it} multiplies every other term in the loop equation in §8.

7. Python: qt.py GUIs, Veusz output and GPU paths

7.1 Test invocation

pytest is documented as invoked either as pytest or through the interpreter as python -m pytest[28]. Inside a sandbox the second form is the one to standardise on, because it removes any doubt about which interpreter is running.

# Whole suite, in the project's own environment.
micromamba run -n Py3p12 python -m pytest -q

# One module, then one test: the node-id forms documented in the pytest
# usage guide. Narrowing like this is how a model should iterate.
micromamba run -n Py3p12 python -m pytest tests/test_sparams.py -q
micromamba run -n Py3p12 python -m pytest tests/test_sparams.py::test_gating -q

# Select by name expression, also documented.
micromamba run -n Py3p12 python -m pytest -k "gating and not slow" -q

7.2 A GUI cannot be tested in a headless sandbox the way it is run

Qt work in this repository uses the qtpy abstraction over PySide6[30]. A container has no display, so a model that writes a Qt test and runs it will see an abort and will not know why.

Approaches to exercising Qt code from a headless sandbox, in increasing order of fidelity and cost.
ApproachWhat it coversCost
Keep the model out of GUI codeNothing. Model works on the computation layer; widgets stay hand-writtenNone. The honest default
QT_QPA_PLATFORM=offscreenConstruction, signals, slots, layout logic. No pixelsOne environment variable
pytest-qt plus offscreenThe above plus event-loop interaction and signal waitingOne dependency
Xvfb virtual display (Linux container)Real rendering, so screenshots are possibleA package and a wrapper command
Host-side runEverything, on the real displayNeeds Route A in §5, and a human looking at it
 
# Offscreen Qt. The platform plugin is chosen by this variable, so the test
# command is otherwise unchanged.
OPEN_TERMINAL_PIP_PACKAGES="pytest pytest-qt"   # or put it in the image

QT_QPA_PLATFORM=offscreen micromamba run -n Py3p12 python -m pytest tests/test_gui.py -q

Say so in the system prompt. "This container has no display. Qt tests must set QT_QPA_PLATFORM=offscreen; do not attempt to screenshot a window." Without that sentence a model will spend iterations rediscovering it, and may conclude the code is broken when the environment is.

7.3 Veusz and plot output

Data-reduction work in this repository writes Veusz output, including the native .vszh5 HDF5 container through h5py[30]. That is well suited to a sandbox: the artefact is a file, so it can be written in the container, checked by assertion, and retrieved through the file browser without any display.

# Verify a plot artefact structurally rather than visually. A model can
# assert on this; it cannot assert on a picture.
micromamba run -n Py3p12 python - <<'PY'
import h5py

# .vszh5 is an HDF5 container, so its structure is inspectable offline.
with h5py.File("out/run_001.vszh5", "r") as handle:
    keys = sorted(handle.keys())
    print("top-level groups:", keys)
    assert keys, "no datasets written"
PY

7.4 GPU work inside the container

A container reaches the GPU only if it was started with access. Docker documents --gpus all for every device, --gpus device=0 for one by index, and --gpus '"device=0,2"' for several, and names the NVIDIA Container Toolkit as the prerequisite alongside the host drivers[26].

# Open Terminal with one GPU, leaving the others for inference. The whole
# point of device= rather than all: a build or a CuPy test must not take
# the card the model itself is running on.
docker run -d `
  --name open-terminal `
  --restart unless-stopped `
  --gpus device=1 `
  -p 8000:8000 `
  -v open-terminal:/home/user `
  -e OPEN_TERMINAL_API_KEY=replace-with-a-long-random-string `
  open-terminal-mamba:0.0.1

# Confirm the device is visible from inside, per the documented example form.
docker exec open-terminal nvidia-smi

Do not hand the model the inference GPU. If the container shares the card that holds the model weights, a CuPy or PyTorch allocation inside a test can exhaust VRAM and abort the model server. Use device= to give the sandbox a different card, or no card at all.

8. Sizing the loop: memory, cores and wall clock

Deciding what hardware this needs means knowing where the time goes. The relation below separates the model's contribution from the toolchain's, and the two worked examples in its derivation reach opposite conclusions about where to spend.

Wall clock of one write-build-test agent task

Derived here
\[ T_{\text{task}} \;=\; N_{\text{it}}\left( \frac{n_{\text{in}}}{r_{p}} \;+\; \frac{n_{\text{out}}}{r} \;+\; T_{\text{build}} \;+\; T_{\text{test}} \right) \]

Sizing a local coding setup means deciding where the time goes. For a small edit on a fast build the model dominates and a bigger model is the wrong trade; for a cold C++ build the compiler dominates and model quality is nearly free, because a better model lowers \( N_{\text{it}} \) and \( N_{\text{it}} \) multiplies everything.

  1. One iteration of the loop is: read context, emit a patch, build, run tests. The agent cannot overlap these, because each step consumes the previous step's output.
  2. Reading \( n_{\text{in}} \) prompt tokens at prefill rate \( r_{p} \) takes \( n_{\text{in}}/r_{p} \). Prefill is compute-bound and batched, so \( r_{p} \) is typically one to two orders of magnitude above \( r \).
  3. Emitting \( n_{\text{out}} \) tokens at decode rate \( r \) takes \( n_{\text{out}}/r \), where \( r \) is bounded by the bandwidth ceiling derived above.
  4. Add the build and test times, then multiply by the number of iterations needed to converge.
  5. Worked example, Python edit. \( N_{\text{it}} = 3 \), \( n_{\text{in}} = 12000 \) at \( r_{p} = 900\ \mathrm{token\,s^{-1}} \), \( n_{\text{out}} = 800 \) at \( r = 15\ \mathrm{token\,s^{-1}} \), \( T_{\text{build}} = 0 \), \( T_{\text{test}} = 6\ \mathrm{s} \). Per iteration: \( 13.3 + 53.3 + 0 + 6 = 72.6\ \mathrm{s} \), total \( 218\ \mathrm{s} \). Generation is 73 % of it, so a faster model wins.
  6. Worked example, C++ edit on an incremental build. Same model figures with \( T_{\text{build}} = 95\ \mathrm{s} \) and \( T_{\text{test}} = 40\ \mathrm{s} \): per iteration \( 201.6\ \mathrm{s} \), total \( 605\ \mathrm{s} \). Generation is now 26 %, so spending that budget on a model that converges in two iterations instead of three saves more than any decode speed-up available.
Symbols in the agent-iteration relation. Measure \(r\) and \(r_{p}\) with the probe script shipped alongside this page set rather than taking advertised figures.
SymbolMeaningUnit
\(T_{\text{task}}\)Wall clock from prompt to passing testss
\(N_{\text{it}}\)Iterations of the write-build-test loop needed to convergedimensionless
\(n_{\text{in}}\)Prompt tokens read per iteration, including re-read source filestoken
\(r_{p}\)Prefill (prompt evaluation) ratetoken·s−1
\(n_{\text{out}}\)Tokens generated per iteration, reasoning traces includedtoken

The conclusion is not symmetric. For Python work, decode speed dominates and the smallest model that gets the answer right wins. For compiled work, the build dominates and model quality is nearly free, because a model that converges in two iterations instead of three saves more than any decode speed-up available locally. Match the model to the language, not to the machine.

9. Model-side settings that decide whether any of this works

Three settings outside the execution backend determine whether a model can use it at all. Each has a failure mode that looks like a broken sandbox.

Model and server settings required for tool-driven code execution, with the symptom each produces when it is wrong.
SettingWhereRequired valueSymptom when wrong
Function Calling Workspace → Models → edit model Native, the default as of v0.10.0 Legacy mode uses prompt-based tool calling, is less reliable, and "may not trigger terminal commands"[5]
Code Interpreter capability Settings → Admin → Models Enabled per model[1] The model writes code and never runs it
OLLAMA_CONTEXT_LENGTH Ollama server environment 32768 or more for agent work Default is 4096[9]. A build log plus source plus history overruns it, the prompt is truncated, and the model loses the error it was fixing

The 4096-token default is the single most common cause of a local agent that "goes in circles". Ollama documents the default context window as 4096 tokens[9]. A C++ compiler error with template instantiation backtraces can be several thousand tokens by itself. Raise OLLAMA_CONTEXT_LENGTH before concluding a model is incapable — then size the result against VRAM with the context-budget relation on the model selection page, because the cache grows linearly with it.

Also relevant: OLLAMA_NUM_PARALLEL has a documented default of 1[9]. An agent loop is bursty rather than concurrent, so 1 is usually right; raising it multiplies the cache term in the same relation.

For the model to reach tools other than the terminal, mcpo proxies an MCP server's stdio interface to REST and OpenAPI. The documented invocations are uvx mcpo --port 8000 -- your_mcp_server_command and the published image ghcr.io/open-webui/mcpo:main[8], with interactive documentation served at /docs.

10. Blast radius and what to lock down

What is being set up here is remote code execution, requested by a language model, on a machine on your network. That is the feature. The question is what it can reach.

Containment properties of each backend, drawn from the Open WebUI documentation's own statements about isolation.
BackendFilesystem reachNetwork reachHost reach
Open Terminal in Docker Container filesystem; OPEN_TERMINAL_FILE_BROWSER_ROOT bounds the browser, and bind mounts are whatever you mounted Unrestricted unless OPEN_TERMINAL_ALLOWED_DOMAINS is set[6] None beyond the container, absent a mounted socket
Open Terminal on bare metal Everything the launching user can read; --cwd sets the served directory but is not a boundary[4] Unrestricted unless allowed-domains is set Full. The documentation calls bare metal a deliberate choice with a wider blast radius[3]
Jupyter engine Everything the kernel's user can read Unrestricted Full. A kernel can subprocess anything
Pyodide Browser virtual filesystem only Browser-mediated None

10.1 Minimum set for a home network

  1. Run Open Terminal in Docker, not bare metal. The documentation's own guidance: use Docker for isolation, bare metal only when the agent should work directly on the host[3].
  2. Set an API key explicitly. OPEN_TERMINAL_API_KEY, or OPEN_TERMINAL_API_KEY_FILE to read it from a Docker secret[6]. An auto-generated key in a container log is not a managed secret.
  3. Bound egress. OPEN_TERMINAL_ALLOWED_DOMAINS listing your package indexes and nothing else. Unset means a model can reach anything you can.
  4. Pin CORS. OPEN_TERMINAL_CORS_ALLOWED_ORIGINS to your Open WebUI origin; the default is * and a start-up warning says so[6].
  5. Firewall per host, not per subnet. Port 8000 admits the Open WebUI host only. The existing rules in this deployment use the whole 192.168.7.0/24 for several services; an execution endpoint deserves narrower.
  6. Mount source read-write, credentials never. Mount the one project directory. Do not mount a home directory, and keep .ssh, cloud credentials and token files out of the container entirely.
  7. Separate the sandbox from the inference host if the inference host serves anyone else.
  8. Treat the workspace as untrusted output. Code a model wrote and a model ran has not been reviewed. Review before it leaves the sandbox.

10.2 A note on the other direction: agent harnesses that enforce a boundary

Open WebUI's backends are containment by deployment choice. A harness such as Claude Code takes the other approach and enforces a boundary at the operating-system level around shell commands, with filesystem and network allowlists in settings.json[21]. The companion page covers that model and how it maps onto the same mamba environments, because the two can be run side by side against one project.

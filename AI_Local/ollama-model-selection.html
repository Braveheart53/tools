Model selection

Which Ollama models are worth running for local code work

A model that writes good code and will not fit on the card is no use, and a model that fits but cannot call a tool cannot drive a build. This page works the constraint from both ends: what the library actually offers for code and agent work, and what the hardware will hold once the key/value cache is accounted for.

Sizes, context windows, capability labels and benchmark figures are quoted from the Ollama model pages cited inline and were read on 2026-10-18. Model pages are revised without notice, so re-check a tag before committing to it. Every computed figure is shown with its derivation.

1. What actually matters when choosing

Five properties decide whether a model can drive the build loop described on the local build and test page. Only two of them are about code quality.

Selection criteria for a model that will write, build and test code locally, in the order they eliminate candidates.
PropertyWhy it decidesHow to check it
Tool calling Without it the model cannot invoke the terminal at all. Open WebUI's terminal integration needs native function calling[5], and a model with no tool support cannot satisfy that however good its code is The tools capability label on the Ollama model page
Context window Source under edit, plus a build log, plus the conversation. A template-heavy C++ error is thousands of tokens by itself Stated per tag on the model page. Then check it against VRAM with the relation in §3 — the advertised window is not the one you get
Weight footprint Weights plus cache plus runtime must fit, or layers spill to system RAM and throughput drops by roughly an order of magnitude Tag size on the model page, checked against the footprint relation
Active parameters Decode rate tracks the parameters read per token, not the total. A routed mixture of experts occupies the card like its total size and streams like its active size Stated on the model page for some models, for example 80B total with 3B active[33]
Agentic training Multi-step tool loops are a distinct skill from single-shot code completion. The Open Terminal documentation notes that small models often struggle with the multi-step loop[3] The model page's own description, and any SWE-Bench or Terminal Bench figure its author published

Tool calling is the hard gate. Of the criteria above, four are tradeable and one is not. A 32B model with excellent code completion and no tool support cannot drive a build at all, while a 4B model with reliable tool calling can — slowly, and with more iterations, but it closes the loop. Filter on tools first and judge quality among what survives.

3. Does it fit? The memory arithmetic

Three terms compete for the same device memory: the weights, the key/value cache, and the runtime's own allocations. The published tag size is only the first of them, and the second is the one that moves when you change a command-line flag.

Quantised weight footprint of a local model

Derived here
\[ S_{w} \;=\; \frac{P\,b_{q}}{8}\,\bigl(1+\varepsilon\bigr) \]

This is the number to compare against free VRAM before pulling a tag. It accounts for the whole weight file, not just the quantised tensors, because a GGUF keeps token embeddings and normalisation weights at higher precision and adds tensor metadata.

  1. A model quantised to \( b_{q} \) bits per weight stores \( P\,b_{q} \) bits of weights in total.
  2. Convert bits to bytes: \( S_{w,\text{raw}} = P\,b_{q}/8 \).
  3. A GGUF container also carries per-tensor metadata and tensors deliberately left at a higher precision. Collect both as a fractional overhead \( \varepsilon \), giving \( S_{w} = (P b_{q}/8)(1+\varepsilon) \).
  4. Check against a published figure. Ollama lists qwen3-coder:30b at 19 GB[11]. Taking \( P = 30.5\times10^{9} \) and the mixed Q4_K_M rate \( b_{q}\approx 4.8\ \mathrm{bit/weight} \): \( (30.5\times10^{9})(4.8)/8 = 1.83\times10^{10}\ \mathrm{B} = 18.3\ \mathrm{GB} \), so \( \varepsilon \approx 0.04 \).
  5. Treat \( \varepsilon \in [0.03,\,0.08] \) as the working range. The Ollama tag page does not state the quantisation level, so the \( b_{q} \) above is the library default rather than a published figure; confirm with ollama show <tag> before relying on the result.

SymbolMeaningUnit
\(S_{w}\)On-disk and in-VRAM size of the weight fileB (byte)

\(b_{q}\)Average bits stored per weight for the chosen quantisation. Representative values: Q4_K_M \(\approx 4.8\), Q5_K_M \(\approx 5.7\), Q8_0 \(\approx 8.5\), BF16 \(= 16\)bit·weight−1

Active parameter count of a routed mixture-of-experts model

Stated
\[ P_{\text{act}} \;=\; P_{\text{shared}} \;+\; k\,P_{\text{expert}} \]

The distinction matters because the two halves of a sizing decision use different parameter counts: VRAM capacity is set by the total \( P \), while decode speed is set by \( P_{\text{act}} \). A 30B model that routes roughly 3B parameters per token occupies the card like a 30B model and streams like a 3B one.

Key/value cache footprint

Derived here
\[ S_{kv} \;=\; 2\,n_{\ell}\,n_{kv}\,d_{h}\,L_{\text{ctx}}\,n_{\text{seq}}\,b_{kv} \]

The cache is the term people forget. It is linear in context length and linear in the number of concurrent sequences, so raising --ctx-size from 8192 to 32768 while also raising --parallel from 1 to 4 multiplies this term by sixteen.

  1. Autoregressive attention caches one key vector and one value vector for every token already generated, for every attention layer. That is the leading factor of 2.
  2. Grouped-query attention shares each key/value pair across several query heads, so the count that matters is \( n_{kv} \), the number of key/value heads, not the number of query heads.
  3. Each cached vector has \( d_{h} \) components, so one token costs \( 2\,n_{\ell}\,n_{kv}\,d_{h} \) elements.
  4. Multiply by the context length \( L_{\text{ctx}} \) that the cache is sized for, and by the number of concurrent sequences \( n_{\text{seq}} \) (--parallel in llama-server), each of which keeps its own cache.
  5. Multiply by the bytes per cached element \( b_{kv} \). Ollama exposes this as OLLAMA_KV_CACHE_TYPE, documented with a default of f16 and options q8_0 and q4_0[9], giving \( b_{kv} = 2,\ 1,\ 0.5\ \mathrm{B} \) respectively.

Longest context a card can actually hold

Derived here
\[ L_{\max} \;=\; \left\lfloor \frac{V_{\text{tot}} - S_{w} - V_{\text{rt}}}{2\,n_{\ell}\,n_{kv}\,d_{h}\,n_{\text{seq}}\,b_{kv}} \right\rfloor \]

A model card advertising a 256K window is stating what the weights were trained to attend over, not what the card in the machine can allocate. This inverts the cache relation to give the second number, which is the one that decides whether a repository-scale prompt fits.

  1. Start from \( S_{kv} = 2\,n_{\ell}\,n_{kv}\,d_{h}\,L_{\text{ctx}}\,n_{\text{seq}}\,b_{kv} \) as derived above.
  2. The cache has to share the device with the weights \( S_{w} \) and with the runtime's own allocations \( V_{\text{rt}} \): compute scratch buffers, the CUDA or Vulkan context, and whatever the display driver has already reserved.
  3. Set the available remainder equal to the cache: \( V_{\text{tot}} - S_{w} - V_{\text{rt}} = S_{kv} \).
  4. Solve for \( L_{\text{ctx}} \) and take the floor, since a partial token cannot be cached.
  5. Round down further in practice. Allocators fragment, and on Windows the WDDM display driver can page VRAM out from under the runtime, so leave headroom rather than sizing to the last megabyte.

SymbolMeaningUnit
\(L_{\max}\)Largest context length that fits once weights and runtime are placedtoken
\(V_{\text{tot}}\)Total device memory on the acceleratorB
\(S_{w}\)Weight footprint, from the quantised-footprint relationB
\(V_{\text{rt}}\)Runtime, driver and compute-buffer reservation. Budget 0.8–1.5 GB for a single-GPU llama.cpp or Ollama process and measure it rather than assumingB
\(n_{\ell},\,n_{kv},\,d_{h},\,n_{\text{seq}},\,b_{kv}\)As defined for the key/value cache relation—

Unit convention on this page: binary, throughout. Every quantity in GB below is a gibibyte, \(2^{30} = 1\,073\,741\,824\) bytes. This matters because the two conventions differ by 7 %, which is comfortably enough to turn a model that does not fit into one that appears to. Binary is the right choice here because it is what the tools report: nvidia-smi reports MiB, and allocation happens in binary units. Treat a vendor's decimal "GB" as the optimistic figure and convert before comparing it against a card. The calculator on the repository homepage uses this same convention, so its results and this page's agree.

4. Will it be fast enough?

Memory-bandwidth ceiling on single-stream decode rate

Derived here
\[ r_{\max} \;=\; \frac{B_{\text{eff}}}{S_{\text{act}}} \qquad\text{and}\qquad r_{\text{obs}} \;\approx\; \eta\,r_{\max},\quad \eta \in [0.5,\,0.8] \]

Token generation is bandwidth-bound, not compute-bound. This single ratio predicts which of two candidate models will feel usable in an agent loop more reliably than any benchmark score does, and it is why an 8-bit quantisation of a model is roughly half the speed of a 4-bit quantisation of the same model.

  1. Generating one token in the decode phase requires reading every active weight from memory exactly once; with a batch of one there is no reuse to amortise that read against.
  2. The time to read \( S_{\text{act}} \) bytes at an achieved bandwidth \( B_{\text{eff}} \) is \( S_{\text{act}}/B_{\text{eff}} \), so \( t_{\text{tok}} \ge S_{\text{act}}/B_{\text{eff}} \).
  3. Take the reciprocal: \( r_{\max} = B_{\text{eff}}/S_{\text{act}} \) tokens per second.
  4. For a dense model \( S_{\text{act}} = S_{w} \). For a routed mixture of experts, substitute \( P_{\text{act}} \) from the active-parameter relation into the quantised-footprint relation instead of \( P \).
  5. Worked example. A 19 GB dense weight set on a card delivering \( B_{\text{eff}} = 450\ \mathrm{GB\,s^{-1}} \): \( r_{\max} = 450/19 = 23.7\ \mathrm{token\,s^{-1}} \), and with \( \eta = 0.65 \) expect about \( 15\ \mathrm{token\,s^{-1}} \).
  6. The same 19 GB file spilled to system RAM at \( B_{\text{eff}} = 50\ \mathrm{GB\,s^{-1}} \) gives \( r_{\max} = 2.6\ \mathrm{token\,s^{-1}} \). That ninefold cliff is the reason the layer-offload count below is worth computing rather than guessing.

Layer count to pass to --n-gpu-layers

Derived here
\[ n_{\text{gpu}} \;=\; \left\lfloor \frac{\bigl(V_{\text{tot}} - V_{\text{rt}} - S_{kv}\bigr)\,n_{\ell}}{S_{w}} \right\rfloor, \qquad 0 \le n_{\text{gpu}} \le n_{\ell} \]

The -ngl value in the service definitions on this page set was chosen by trial. This gives a starting value to try first, which matters because the failure mode of overshooting is an out-of-memory abort part-way through loading rather than a graceful fallback.

  1. llama.cpp offloads whole transformer blocks, so the granularity is one layer. Averaged over the stack, one layer is \( S_{w}/n_{\ell} \) bytes.
  2. The device must also hold the runtime reservation \( V_{\text{rt}} \) and the whole key/value cache \( S_{kv} \), both of which are allocated regardless of how many layers are resident.
  3. The bytes left for weights are therefore \( V_{\text{tot}} - V_{\text{rt}} - S_{kv} \).
  4. Divide by the per-layer size and take the floor: \( n_{\text{gpu}} = \lfloor (V_{\text{tot}} - V_{\text{rt}} - S_{kv})\,n_{\ell}/S_{w} \rfloor \).
  5. Clamp into \( [0,\,n_{\ell}] \), then subtract one or two before the first run. Layers are not uniform in size, the output projection is usually the largest single tensor, and allocator fragmentation costs real megabytes.
  6. If the result equals \( n_{\ell} \), pass -ngl 999 rather than the exact count so the setting survives a change of model.

The cliff is the thing to avoid. The derivation above shows the same 19 GB weight set running about nine times slower from system RAM than from VRAM. Every other decision on this page — quantisation, cache type, context length, how many layers to offload — is in service of staying on the fast side of that cliff. A smaller model fully resident beats a larger model that spills, essentially always.

5.1 Two models, not one

Nothing requires a single choice. The loop equation on the build page shows that generation dominates fast Python iterations while the compiler dominates C++ ones, so a sensible local setup keeps two models loaded and routes by task.

A two-model arrangement, with the Ollama setting that makes it work. Both models stay resident so there is no reload penalty on switching.
RoleModelUsed for
Fast pathqwen2.5-coder:7b or nemotron-3-nano:4bSingle-file edits, test stubs, docstrings, quick refactors. Decode speed is what matters
Deep pathdevstral-small-2:24bMulti-file changes, build failures, anything where converging in fewer iterations is worth waiting for

Keeping both resident needs OLLAMA_MAX_LOADED_MODELS, documented with a default of "3 * the number of GPUs or 3 for CPU inference"[9], so the default already permits two. The binding constraint is VRAM: the two footprints and both caches must fit simultaneously, or Ollama will evict one and reload it on every switch. OLLAMA_KEEP_ALIVE, with a documented default of five minutes[9], controls how long an idle model stays loaded.

6. When the model does not fit on one machine

llama.cpp's RPC backend splits the layer stack across machines[17], which is how this deployment runs models larger than any single card. The RPC and Vulkan guide covers the mechanics; the arithmetic below decides whether a given split is worth doing.

Read the upstream warning before exposing a worker. The RPC README marks the backend as a proof of concept and states plainly: “the functionality is fragile and insecure. Never run the RPC server on an open network or in a sensitive environment!”[37] There is no authentication on the worker port. The firewall rules this deployment uses admit only the inference host by address, which is the minimum that makes this safe, and the workers should not be reachable from anywhere else on the network.

The worker binary has been renamed. It is now ggml-rpc-server, not rpc-server[37], and started with no arguments it exposes every accelerator it finds. Restrict that with --device CUDA0 or CUDA_VISIBLE_DEVICES, which the README gives as equivalent:

$ CUDA_VISIBLE_DEVICES=0 bin/ggml-rpc-server -p 50052
$ bin/ggml-rpc-server --device CUDA0 -p 50052

Two further options are worth knowing. -c enables a local tensor cache, which avoids re-transferring large tensors over the network and speeds model loading noticeably; it lives under $HOME/.cache/llama.cpp/rpc and follows LLAMA_CACHE. GGML_RPC_DEBUG raises log verbosity on either end when a split misbehaves[37].

The default split is proportional, not manual. llama.cpp distributes model weights and the key/value cache across every available device, local and remote, in proportion to each device's free memory, and --tensor-split overrides those proportions[37]. This matters for the relations below: the per-node weight term \( S_{i} \) is something the runtime chooses for you unless you set it, and the cache is split too rather than sitting entirely on the host.

Per-token wall clock across RPC workers

Derived here
\[ t_{\text{tok}} \;=\; \sum_{i=1}^{N}\frac{S_{i}}{B_{i}} \;+\; \sum_{i=1}^{N-1}\left(\frac{D_{\text{act}}}{R_{i}} + 2\tau_{i}\right), \qquad r \;=\; \frac{1}{t_{\text{tok}}} \]

llama.cpp's RPC backend splits the layer stack across machines[17]. This separates the part of a token's cost that the split reduces from the part it adds, which is the only way to answer whether a fourth node is worth switching on. Note that \( S_{i} \) is chosen for you by default: the runtime distributes weights and the cache across every local and remote device in proportion to free memory, unless --tensor-split says otherwise[37].

  1. Node \( i \) holds \( S_{i} \) bytes of the weight set and streams them from its own memory at \( B_{i} \), so its contribution to one token is \( S_{i}/B_{i} \) by the bandwidth-ceiling argument above.
  2. A pipeline split is sequential for a single token: layer \( j+1 \) cannot start before layer \( j \) has produced its output. The per-node times therefore add rather than overlap.
  3. At each of the \( N-1 \) boundaries the activation tensor of \( D_{\text{act}} \) bytes crosses the link at throughput \( R_{i} \), costing \( D_{\text{act}}/R_{i} \), plus \( 2\tau_{i} \) for the request and response legs.
  4. Summing both contributions gives \( t_{\text{tok}} \), and \( r = 1/t_{\text{tok}} \).
  5. Scale of the link term on a home network. One activation row for a hidden size of 4096 in f16 is \( 4096 \times 2 = 8192\ \mathrm{B} \). Over gigabit Ethernet at an achieved \( R = 940\ \mathrm{Mbit\,s^{-1}} = 1.18\times10^{8}\ \mathrm{B\,s^{-1}} \) that is \( 69\ \mathrm{\mu s} \), against \( 2\tau \approx 400\ \mathrm{\mu s} \) for a typical switched round trip. Latency dominates transfer, so the number of hops matters more than the hidden size.
  6. Prompt processing behaves differently. It submits many tokens at once, so \( D_{\text{act}} \) scales with the batch and the transfer term stops being negligible.

Break-even condition for adding an RPC worker

Derived here
\[ \frac{S_{m}}{B_{\text{host}}} \;>\; \frac{S_{m}}{B_{\text{worker}}} \;+\; \frac{D_{\text{act}}}{R} + 2\tau \]

Read as: moving \( S_{m} \) bytes of weights onto a worker pays only when the time the host stops spending on them exceeds the time the worker spends plus the cost of the extra hop. The condition is almost always satisfied when the bytes were spilling to host RAM, and almost never when they already fit in host VRAM.

  1. Write \( t_{\text{tok}} \) from the relation above for the configuration before the move, with \( S_{m} \) bytes still on the host: the host contributes \( S_{m}/B_{\text{host}} \).
  2. Write it again after the move: the worker contributes \( S_{m}/B_{\text{worker}} \), and one new boundary contributes \( D_{\text{act}}/R + 2\tau \).
  3. Every other term is common to both expressions and cancels.
  4. The move reduces \( t_{\text{tok}} \) exactly when the removed term exceeds the two added terms, which is the inequality stated.
  5. Case that pays. \( S_{m} = 6\ \mathrm{GB} \) spilling to host RAM at \( B_{\text{host}} = 50\ \mathrm{GB\,s^{-1}} \) costs \( 120\ \mathrm{ms} \) per token. On a worker GPU at \( B_{\text{worker}} = 400\ \mathrm{GB\,s^{-1}} \) it costs \( 15\ \mathrm{ms} \), plus roughly \( 0.5\ \mathrm{ms} \) of link cost from the figures above. The move saves about \( 105\ \mathrm{ms} \) per token.
  6. Case that does not. The same \( 6\ \mathrm{GB} \) already resident in host VRAM at \( 450\ \mathrm{GB\,s^{-1}} \) costs \( 13.3\ \mathrm{ms} \). A worker at \( 400\ \mathrm{GB\,s^{-1}} \) costs \( 15\ \mathrm{ms} \) plus the hop, so the move loses about \( 2.2\ \mathrm{ms} \) per token and adds a failure domain.

The rule the break-even condition reduces to. Distribute to escape a spill, never to add bandwidth. Moving weights that were spilling to host RAM onto a worker GPU is a large win; moving weights that already sat in host VRAM is a small loss plus a new failure domain. Check which case you are in before switching a worker on.

7. Measure it yourself

Every rate on this page is computed from a bandwidth figure, and a computed rate is a prediction. The script shipped with this page set, scripts/probe_model_throughput.py, measures the real thing through the Ollama API and prints the measured rates alongside what the relations predict.

# Measure the shortlisted models against the relations on this page.
